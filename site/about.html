The problem with system design material

Every resource has the same shape: a list of concepts, a diagram of a URL shortener, and a promise that you will pass the interview. You read it, nod, and two weeks later cannot explain why your own service fell over.

The reason is that design knowledge does not transfer by reading. "Consistent hashing reduces key movement" is a sentence you can memorise without understanding a thing. But implement the naive version, measure that adding one server to a four-node cache moves 81% of your keys, then implement the ring and watch it drop to 20% — now you know something you cannot un-know, and can rederive under pressure.

Four lesson types

System design does not decompose the way machine learning does. In an ML curriculum you can implement backprop and verify it numerically. There is no equivalent for "design a news feed" — the artifact is a judgement, not a passing test.

Pretending otherwise produces the standard failure: hundreds of pages of prose with nothing to run. So each topic is matched to what it actually is.

  • Concept — the default, and most of the curriculum. The mechanism in pseudocode, a measured result, and a script to run and change. Knowing when to shard is the skill; hand-writing a hash ring is not.
  • Build — reserved for the few topics where writing the mechanism is itself the insight: consensus, leader election, rate limiting under real concurrency, write-ahead logs.
  • Simulate — for systems too large to build. Model the load and measure the trade-off: watch p99 drop when a cache is added, and watch staleness appear alongside it.
  • Design — for judgement with no unit test. A brief, a self-scoring rubric, a table of traps, and a reference direction labelled as a strong answer.

Tests assert the teaching

Ordinary tests check correctness. These also check that the idea holds, so a refactor that breaks a lesson fails with a message naming the property that died: 

TestModuloRemapsNearlyEverything   fails if modulo churn drops below 70%
TestRingMovesOnlyItsShare          fails if ring churn exceeds 35%
TestRingBeatsModuloByAtLeast2x     fails if the gap ever closes
TestSpreadPlateaus                 records where extra virtual nodes stop paying

When the measurement wins

This has already happened once, in the first lesson written. A test asserting "more virtual nodes always improve load balance" failed against the real implementation. Balance plateaus around 50 replicas, and 500 can score worse than 150 — noise in a flat region, not a trend.

So the lesson now teaches the plateau, and cites why Cassandra reduced its default num_tokens from 256 to 16. The plausible belief was wrong and the measurement caught it. That is the method working, and it is the standing rule: when a measurement contradicts a lesson, the lesson changes.

Pseudocode, and Python behind it

The subject is system design, not a programming language. So each mechanism is written as pseudocode — readable whatever you work in, and impossible to skip because it is in a language you do not use.

Behind every lesson sits one Python script whose only job is producing the numbers the lesson quotes. Standard library only, so it runs on a fresh machine with nothing installed. You mostly read and run it rather than write it — it exists so that every "it depends" ends in a figure you can reproduce and check.

How the site is built

node site/build.js scans the phases/ directory and generates the catalog. The source of truth is the filesystem, not a hand-maintained list, so the site cannot advertise a lesson that has not been written. Planned lessons come from curriculum.json and render as explicitly unavailable.

There is no framework and no bundler. Lesson pages fetch the markdown straight from the repository and render it with a small auditable parser (site/md.js, 59 tests, 17 of them for HTML escaping and URL safety). Agents can read llms.txt for a link-rich map of the curriculum.

The rule

No claim without a number the lesson produced. The audit script enforces it — a doc quoting figures its own code no longer prints fails the build. That check is why this is not simply a blog post with more sections: every trade-off here terminates in something you can rerun.

Contributing

The most valuable contribution is finding a claim the code does not support. If a lesson asserts something its own code fails to demonstrate, that is the highest-value bug report here — open an issue even without a fix.
