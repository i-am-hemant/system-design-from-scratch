Build the mechanisms. Measure the trade-offs.

Most system design material teaches you to recite answers. This teaches you to derive them. You implement the algorithms in Go, measure what they cost, and defend your designs against a rubric — because a trade-off you cannot measure is one you are taking on faith.

The whole idea in one measurement

"Consistent hashing reduces key movement" is a sentence you can memorise without understanding. So don't memorise it — run it. This is real output from the lesson's code, comparing naive modulo mapping against a hash ring as the cluster grows:

go run ./cmd/churn
CHANGE           MODULO   RING    IDEAL   RING vs MODULO
2 -> 3 nodes     66.9%    34.3%   33.3%   2.0x better
4 -> 5 nodes     81.0%    25.1%   20.0%   3.2x better
8 -> 9 nodes     89.2%     7.8%   11.1%   11.4x better
16 -> 17 nodes   94.6%     6.5%    5.9%   14.6x better
32 -> 33 nodes   97.1%     3.8%    3.0%   25.7x better
64 -> 65 nodes   98.5%     1.1%    1.5%   86.4x better

Adding one server to a four-node cache remaps 81% of keys — every one a cache miss hitting the database, exactly when you were already under load. Note the shape: modulo gets worse as you scale, the ring gets better. No paragraph conveys that like the numbers do.

Three kinds of lesson

System design does not decompose the way machine learning does. You can implement backprop and verify it numerically; you cannot implement "design a news feed." So the curriculum is honest about which kind of thing each topic is.

Build

Code the primitive

Some topics are genuine algorithms: hash rings, token buckets, bloom filters, write-ahead logs, leader election, circuit breakers. You implement them in Go with tests that assert the trade-off, not just correctness.

Simulate

Measure the trade-off

You cannot build DynamoDB in a lesson. You can simulate load and watch p99 fall when you add a cache — and watch staleness appear. Trade-offs become numbers you generated yourself.

Design

Defend the judgement

Some answers have no unit test. These ship a brief, a self-scoring rubric, a table of traps, and a reference direction — labelled as a strong answer, never the answer.

Tests that assert the teaching

Ordinary tests check that code is correct. These also check that the idea still holds, so a refactor that breaks the lesson fails loudly: 

func TestModuloRemapsNearlyEverything(t *testing.T)  // fails if modulo churn drops below 70%
func TestRingMovesOnlyItsShare(t *testing.T)         // fails if ring churn exceeds 35%
func TestRingBeatsModuloByAtLeast2x(t *testing.T)    // fails if the gap ever closes
func TestSpreadPlateaus(t *testing.T)                // records where extra vnodes stop paying

This keeps the curriculum honest about itself. While writing the first lesson, a test asserting "more virtual nodes always improve balance" failed — because it isn't true. Load balance plateaus around 50 replicas, and 500 can score worse than 150. The lesson now teaches the plateau, and cites why Cassandra reduced its default num_tokens from 256 to 16.

That outcome is the method working: a measurement overruled a plausible belief.

Who it's for

  • Beginners — start at phase 1 and go in order. Everything runs on your laptop with the Go toolchain and nothing else.
  • Working engineers — jump to the lesson for the thing you're about to build. Each has a "what this does not solve" section you'll want before committing.
  • Interview prep — the design exercises are the closest thing here to a real interview, and the rubrics tell you what a strong answer names.

No prior distributed-systems knowledge assumed. Basic Go is enough — the code avoids clever constructs on purpose.
